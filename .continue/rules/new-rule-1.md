# Rule: Match Local Project Style

## Purpose
Ensure that any Python code generated by the assistant **blends seamlessly with the existing codebase**. Generated code must adopt the **same style, structure, and conventions** used in other files or classes within the same project.

## Behavior Requirements

1. ✅ **Naming Conventions**
   - Match function, class, variable, and constant naming style:
     - `snake_case`, `camelCase`, `PascalCase`, or `UPPER_CASE` as used in the project.
   - Detect and preserve project-specific patterns (e.g., prefixes like `get_`, suffixes like `_impl`).

2. ✅ **Docstring Style**
   - Automatically infer and match the dominant style:
     - Google style
     - NumPy style
     - reStructuredText
   - If no clear style is dominant, default to **Google style**.

3. ✅ **Import Style**
   - Respect existing import conventions:
     - Absolute vs. relative imports.
     - Explicit `from ... import ...` vs. `import module as ...`.

4. ✅ **Function & Class Structure**
   - Match indentation, method order, property usage, and error-handling patterns.
   - Maintain spacing and layout consistency (e.g., blank lines before/after methods).
   - Adopt patterns like single-line functions, early returns, or inline `if` expressions if they are commonly used.

5. ✅ **Type Hints**
   - Include or exclude type hints based on local usage:
     - If most functions have full annotations → use full type hints.
     - If annotations are sparse → follow minimal or inferred style.
   - Match Python version support (e.g., `list[int]` vs `List[int]`).

6. ✅ **Formatting and Linting Compatibility**
   - Ensure generated code still passes **Ruff** and **Pylance** checks.
   - If the project has a `pyproject.toml`, `.ruff.toml`, or `.editorconfig`, respect its rules.
